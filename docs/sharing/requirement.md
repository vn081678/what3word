## Preconditions

- The public what3words map is available at `https://what3words.com/`.
- A valid location is selected; its what3words address and canonical URL are visible, and the `Share` action is enabled.
- The visitor has a working internet connection.
- Pop-ups and external application links are permitted for the test.

## Scope and ownership

- what3words owns the Share interface, the selected-location payload, URL construction, encoding, and initiation of the external share target.
- SMS carriers, email clients, X, Facebook, WhatsApp, operating systems, and browsers own authentication, delivery, posting, previews, native rendering, and application routing after the payload leaves what3words.
- A failure in a third-party system is a what3words defect only when the target or payload supplied by what3words is incorrect, incomplete, stale, unsafe, or incompatible with the documented platform contract.

## Functional requirements

### REQ-SH-001 - Display sharing channels

When the visitor selects `Share` for the selected location, the application must display sharing options for SMS, Email, X, Facebook, and WhatsApp.

The share content must identify the selected location using its what3words address or canonical what3words URL.

### REQ-SH-002 - Close and restore focus from the Share interface

The visitor must be able to close the Share interface without selecting a channel. Closing it by its visible close control or the Escape key must return keyboard focus to the `Share` action and must not initiate an external share target.

### REQ-SH-003 - Generate safe, location-specific share targets

Each channel target generated by what3words must use an expected HTTPS platform host or registered operating-system handler, must contain only the intended selected-location content, and must not expose authentication tokens, account identifiers, or stale data from a previously selected location.

### REQ-SH-SMS-001 - Open an SMS draft

When the visitor selects the SMS sharing option, the application must open the device's SMS handler with a message containing the selected location's what3words address or canonical what3words URL.

### REQ-SH-SMS-002 - Preserve SMS content within message segments

The SMS payload generated by what3words must contain the complete explanatory copy, selected what3words address, and canonical URL before it is passed to the operating-system handler.

The payload character count must be recorded so that changes to message length and the resulting device-level segmentation can be reviewed. Carrier or device segmentation is a compatibility observation rather than a what3words functional requirement.

### REQ-SH-SMS-003 - Provide a valid location link in SMS

The generated SMS must contain one complete canonical what3words HTTPS URL for the selected location. The link must contain no whitespace, must not expose malformed or double percent-encoding, and must open the same what3words address that was selected when the SMS draft was created.

### REQ-SH-SMS-004 - Open the shared location on the recipient device

After a generated SMS is delivered to a recipient, the received message must preserve the complete canonical what3words URL as an actionable link. When the recipient activates the link, the recipient's browser must open what3words and display the same what3words address selected by the sender.

### REQ-SH-EMAIL-001 - Open an email draft

When the visitor selects the Email sharing option, the application must open the configured email handler with a new, unsent draft.

### REQ-SH-EMAIL-002 - Compose email subject and body

The generated email draft must contain:

1. A non-empty subject that identifies the message as a shared what3words location.
2. Static explanatory copy that remains unchanged when different locations are selected.
3. The currently selected what3words address as dynamic content.
4. The currently selected canonical what3words URL as dynamic content.
5. No address or URL retained from a previously selected location.

### REQ-SH-EMAIL-003 - Preserve email characters and readability

The generated email subject and body must preserve the source text and selected what3words address without replacement characters, missing glyphs, mojibake, unexpected HTML source, or percent-encoding displayed to the recipient.

The generated source must not contain unintended raw HTML or CSS. Client-controlled fonts, layout, and appearance modes are compatibility observations.

### REQ-SH-EMAIL-004 - Open the selected location from the email deep link

The canonical what3words URL in the generated email must be an actionable HTTPS link. Activating it must open what3words and display the same what3words address that was selected when the draft was created.

### REQ-SH-EMAIL-005 - Provide portable email content

The email subject and body generated by what3words must preserve their complete content when passed to supported Gmail, Outlook, and Apple Mail handlers. If what3words supplies plain text, no raw HTML or CSS must be displayed. If product design confirms that what3words supplies HTML, the supported markup and styling must be defined before HTML rendering becomes an acceptance criterion.

### REQ-SH-X-001 - Open the X post composer

When the visitor selects the X sharing option, the application must open an X-owned share target with an editable, pre-populated post. The composer must contain the selected location's canonical what3words URL and must not publish without explicit visitor confirmation.

If the visitor is not authenticated, X must be allowed to request authentication before presenting or publishing the post.

### REQ-SH-X-002 - Preserve a valid X post payload

The pre-populated X post must retain its intended explanatory text and one complete canonical what3words URL without truncation, malformed encoding, or stale data from a previously selected location.

The payload supplied by what3words must be accepted by the standard X post composer without product-owned text or the URL being truncated.

### REQ-SH-X-003 - Cancel X sharing without publishing

When the visitor closes or cancels the X composer before selecting `Post`, no post containing the shared location must appear on the visitor's X profile.

### REQ-SH-X-004 - Open a published X location link

After a controlled test post is published, its link must remain actionable. Activating the link from the published post must open what3words and display the same what3words address selected by the sender.

### REQ-SH-FB-001 - Open the Facebook Share Dialog

When the visitor selects the Facebook sharing option, the application must open a Facebook-owned Share Dialog for the selected location's canonical what3words URL. The dialog may be presented as a popup, page, or touch interface according to the device and authentication state, and must not publish without explicit visitor confirmation.

### REQ-SH-FB-002 - Display the selected location preview

The Facebook Share Dialog must associate its shared `href` with the selected location's canonical what3words URL. The shared page must expose valid Open Graph metadata for the preview fields supported by the product. Whether preview metadata is generic or location-specific must match the product-approved metadata contract.

### REQ-SH-FB-003 - Cancel Facebook sharing without publishing

When the visitor closes or cancels the Facebook Share Dialog before confirming the share, no story containing the selected location must appear on the visitor's Facebook timeline.

### REQ-SH-FB-004 - Open a published Facebook location link

After a controlled test story is published, its link must remain actionable. Activating the link from the published story must open what3words and display the same what3words address selected by the sender.

### REQ-SH-WA-001 - Open a WhatsApp share target

When the visitor selects the WhatsApp sharing option, the application must open a WhatsApp-owned recipient-selection or chat interface with an editable, prefilled message. The message must not be sent until the visitor selects a recipient and explicitly confirms sending.

The flow may use the installed WhatsApp application, WhatsApp Desktop, or WhatsApp Web according to the device and available handler.

### REQ-SH-WA-002 - Preserve the WhatsApp share payload

The prefilled WhatsApp message must contain the selected location's what3words address and one complete canonical HTTPS what3words URL. It must preserve spaces, line breaks, punctuation, and Unicode characters without truncation, mojibake, malformed percent-encoding, double encoding, or stale data from a previously selected location.

### REQ-SH-WA-003 - Cancel WhatsApp sharing without sending

When the visitor closes or cancels recipient selection or the WhatsApp composer before selecting `Send`, no message containing the shared location must appear in any conversation.

### REQ-SH-WA-004 - Open the shared location on the WhatsApp recipient device

After a controlled WhatsApp message is delivered, the received message must preserve the complete canonical what3words URL as an actionable link. Activating it on the recipient device must open what3words and display the same what3words address selected by the sender.

### REQ-SH-WA-005 - Display an accurate WhatsApp link preview

The shared location page must expose valid metadata that allows WhatsApp to identify what3words and the intended destination when the client generates a preview. Preview generation, caching, and rendering remain WhatsApp-owned behavior.

### REQ-SH-WA-006 - Route sharing from a desktop browser

From a supported desktop browser, the WhatsApp share action must preserve the selected-location payload while initiating WhatsApp Web, a linked desktop application, or a usable login, device-linking, or application-choice flow.

### REQ-SH-WA-007 - Route sharing from a mobile browser

From a supported Android or iOS browser, the WhatsApp share action must preserve the selected-location payload while initiating the installed WhatsApp application. When no native handler is available, the browser must receive a usable web or installation route instead of a malformed or empty target.

## Assumptions and volatile dependencies

- Except for the controlled external journeys in REQ-SH-SMS-004, REQ-SH-X-004, REQ-SH-FB-004, and REQ-SH-WA-004, the requirements cover creation of the share target and payload rather than successful delivery, posting, or authentication.
- SMS and Email depend on a configured operating-system handler. WhatsApp may use the installed application or its web client.
- SMS segment capacity depends on its encoding: a single GSM-7 message supports 160 septets and concatenated segments normally carry 153 septets each; a single Unicode message supports 70 characters and concatenated segments normally carry 67 characters each. Extended GSM-7 characters may consume two septets.
- No product-specific maximum SMS length has been confirmed. The current requirement checks complete content and correct segmentation rather than requiring every share message to fit one segment.
- X, Facebook, and WhatsApp can change their share endpoint, authentication screen, and visual design without a what3words product change.
- X automatically processes posted URLs through `t.co`; the displayed link can differ from the original while retaining the same destination.
- X currently counts a processed URL as 23 characters. This is a platform compatibility rule, not a permanent what3words acceptance criterion.
- Facebook controls authentication, dialog presentation, privacy selection, and preview caching. A stale Facebook preview must be distinguished from an incorrect what3words `href` or Open Graph response.
- WhatsApp controls application selection, authentication or device linking, delivery state, and link-preview generation. Link previews can depend on client settings, network access, and cached metadata.
- The exact wording around the shared address is not specified; the selected what3words address or canonical URL is the required stable content.
- Gmail, Outlook, and Apple Mail control native fonts, link styling, and dark-mode transformations. The product requirement is readable, complete content rather than pixel-identical rendering.
- The supported client versions and operating systems must be recorded during execution because email-client rendering changes over time.
- Email HTML/CSS output has not been confirmed. Until it is confirmed, plain-text subject, body, encoding, and deep-link behavior are the product-owned acceptance contract.
